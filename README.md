## 抓包解析工具

`tools/parse_hci_log.js`：解析安卓蓝牙 HCI 日志（**btsnoop** / **pcap**，含 vivo 的 `.cfa`），用于还原官方小程序/APP 刷机时**真实发出去的字节**。

```bash
node tools/parse_hci_log.js <btsnoop或cfa文件> [--full]
```

输出（对 `BT_HCI_*.cfa` 实测）：

- **连接与链路事件**：连接/断开（含断开原因）、连接参数（监督超时）、MTU 协商、CCCD 订阅；
- **设备广播**：从广播/扫描应答里提取可读串（如 `*WITRN&W96D001@10|DFU#`）；
- **DFU 命令 → 应答时序表**：每条命令的解码名称、应答延迟、解掩码后的应答内容（`0x8F→SN`、`0x85→01/02`、`0x8C→05 00 10`、`0x81+头96B→02` …）；
- **数据阶段统计**：帧数、覆盖字节数、间隔 min/中位/max、帧率（实测 639 帧 / 81764B / 中位 18ms / 54.8 帧每秒）；
- 句柄统计、完整写入/通知序列、≥20B 大帧字节。

> 早期合成 btsnoop 的验证（正确分离带响应写的小帧与无响应写的大帧、解出 `55 00 61 00 81 …`）已由上面这份真实抓包取代并验证。

## OTA 固件升级（已内置，v20260925f）

**结论（2026-09-25，依据官方小程序成功刷机的抓包）**：协议彻底打通，工具里**已实现**刷机。

**当年卡住的根因**：不是帧长、不是 key、不是写入类型（这些我们早已与小程序逐字节一致），而是 **`0x8F` 的发送时机**——必须在 `0x84 ENTER_DFU` 的应答之后**立刻（实测 59ms）、在同一条旧连接上**发出。我们此前是**等断链重连之后**才发，设备那时只把它当普通 SN 查询回 `0a+SN`，**切换从未发生**，于是后续 102B 解锁帧被静默丢弃。

**抓包实证的流程**（完整时序见报告 §2.4.0）：

```
0x0F/0x8F GET_SN → 0x8A GET_VERSION → 0x85(→01 应用态) → 0x84(→02) → 0x8F(同连接立刻发, 无应答)
→ 等断链(设备侧 5s 监督超时, reason 0x08) → 重连(MTU 由 243 变 247) → 重新订阅 FEE2
→ 0x85(→02) → 0x8C(→05 00 10, 页 4096) → 0x81+头96B(102B 整帧 → 02) → 0x87(→02, 约 1.3s)
→ 638×128B + 100B 尾帧(共 81764B, 无逐块回执, ~18ms/帧) → 0x88(→02) → 0x0B(复位)
```

### 怎么用

1. 蓝牙连接 NEW W96D / W96Pro → **设备信息页** → 卡片 **⬆ 固件升级 OTA**；
2. 选择固件 `.up`（官方 `W96DN_V1.3.zip` 解出的 `W96D_V13.up`，本仓库 `rom/` 里有）；
3. 先点 **🧪 干跑（不擦除）**：只走到"已进入传输阶段"，用来确认通路（**不发 `0x87`，不掉固件**）；
4. 再点 **⬆ 开始升级**：确认弹窗后开始，进度条显示写块进度，全程约 15s（639 帧）；
5. 完成后设备自动重启，等 5~10s 重新连接即可。

**安全边界**：`0x87` 之前**不发任何会写 flash 的命令**；`0x87` 之后应用区已被擦除，**切勿断电/关页面**。失败时报错会明确说明"是否已擦除"：`0x87` 前失败 ⇒ 应用区完好，直接重试；`0x87` 后失败 ⇒ 设备停在 DFU 阶段，重新连接后再刷一次即可。

**已用 mock 全流程验证**（`/tmp/ota_test.js`，喂真实固件字节）：写入 650 条、数据 639 帧、**拼接结果与固件体 81764B 逐字节一致**、首/末帧长 134/106B、`0x0B` 是最后一帧、干跑阶段无擦除类命令；并断言 `0x8A`/`0x0F`/`0x8C` 的应答真的被消费（不是走兜底值）—— 全部断言通过。

**★ 收尾（2026-09-25 真机第二次试跑）：CRC 修好后 `0x81+头96B → 02`、`0x87 → 02`、639 块全部发完（81764B/14.5s），但 `0x88`（结束传输）10s 内无应答。**

设备收尾（把最后几页写进 flash + 校验）可能远慢于抓包里的 133ms，因此 v20260925e 起：
- `0x88` 改成 **最多 3 次、每次等 20s**；期间若设备自行断链 ⇒ 判定为"重启中＝升级完成的正常表现"；
- 彻底没应答时，**反问设备 `0x85`**：回 `02` ⇒ "仍在传输阶段，本次写入未被接受，请重刷"；回 `01` ⇒ "已回到应用模式，固件已生效"；
- 最后**轮询回读版本**（`0x8A`；设备重启期间读不到就等它回来重连再读），并把"刷机前版本 → 刷机后版本"一起显示（同版本重刷时版本号不变，属正常）；
- 新增 **「帧间隔」输入框（默认 20ms）**：抓包实测官方小程序 ≈18ms，若判定"有块丢失"，放慢到 30~40ms 再刷一次。
  回归：`/tmp/ota_endfail_test.js` 覆盖两条收尾失败分支（`0x88` 无应答 + `0x85→02` / `0x85→01`）。

**★ 真机结果（2026-09-25 01:32）**：CRC 修正 + 收尾加固后**刷机成功** —— `0x81+头96B→02`、`0x87→02`、639 块（81764B/13.3s）、`0x88` 第 2 次重试拿到 `02`、`0x0B` 复位后设备重启断链。

**★ 真凶（2026-09-25 真机跑通后由抓包反查，已修 v20260925d）：CRC8 表里有两个错值**

官方网页 `W96D_V3.8.html` 的 CRC8 表把**下标 120 与 202 两处误写成 `200`**（正确值 `102`/`101`），工具当初"以官方为准"照抄了这张表；而**官方小程序用的是数学上正确的 poly=0x3B（非反射，初值 0x89）表**。用抓包里 **657 条帧**验证：

| 帧类型 | 原表（=官方网页） | poly=0x3B 真值表 |
|---|---|---|
| 6B 控制帧（17 条） | 17/17 | 17/17（两表在这些输入上恰好同值） |
| 102B 解锁头 | **0/1** | 1/1 |
| 106B 尾帧 | **0/1** | 1/1 |
| 134B 数据帧（638 条） | 251/638 | **638/638** |

短帧算不到那两个错项 ⇒ 所有 6~10B 控制命令一直正常，从没让人怀疑 CRC；**一旦载荷变长，运行中的 CRC 就会命中错项 ⇒ 校验字节算错 ⇒ 设备静默丢弃**。这就是"102B 解锁帧怎么发都没反应"的真凶：不是帧长、不是写入类型、不是时序，而是 CRC 错了。

修正后新增**黄金帧回归**（`/tmp/golden_frame_test.js`）：用抓包里小程序真实发出的每一帧与工具 `dfuPack()` 逐字节比对 —— `102B 解锁头 ✓｜638×134B 数据 ✓ 638/638｜106B 尾帧 ✓`，即帧布局与 CRC 算法与成功刷机完全一致（修正前长帧 0/640）。短帧新旧表 CRC 完全相同，已正常工作的命令不受影响。

**另一次真机试跑踩到的坑（已修，v20260925c）**：重连后第二次 `0x85` 的 `02` 应答**其实收到了**，但末尾校验字节不符：

```
[RX] ⚠第 CRC 校验失败，丢弃一帧：key=0x9 len=1 payload=02      ← 结构完整、载荷正确，只有校验字节不符
[00:52:02] !! OTA 异常/中止: DFU 超时
```

掩码解出来是 `len=1 / payload=02`，即设备明确确认了传输阶段，却因为**一个校验字节**被丢掉，OTA 直接中止。修法（都在 `W96D统一控制台.html` 内）：

1. **宽容采用**：CRC 不符但结构完整（`0x55` 头 + 合法长度 + 完整载荷）时**采用该载荷**并显著留痕（原始通知字节、期望/实际 CRC 都打出来）——BLE 链路层本身已有 CRC16，且掩码/长度/载荷三者自洽；
2. **减少握手往返**：重连时 `dfuWaitReconnect` 已校验过一次 `0x85`，结果记在 `S.ble.lastCheckIn`，不再重复发一轮（那次重复正是踩坑点）；
3. `0x8C`（页大小）与 `0x81`（文件头）各加**一次重试**（都是非破坏性命令）；
4. 超时时打印"残留半帧"（已收字节数 + 最近一条通知的原始字节），下次再遇到可直接定位。
   回归：`/tmp/crc_lenient_test.js`（故意写错应答的 CRC 字节 → 断言仍能取到载荷、且整条 OTA 能跑完 639 帧）。

**首次真机验证可以放心用 `rom/W96D_V13.up`**：抓包证明小程序刷的就是这份固件（解锁帧里的 96B 头部与它**逐字节一致**），而且设备当时跑的就是 V1.3 ⇒ **同版本可以重刷**，不需要"版本号 +1"的测试包。

**顺手修掉的一个真 bug**：`dfuRequest` 会丢弃不在 expect 列表里的应答，而解锁帧的真实应答是 **`02`**，此前的 expect 列表 `[0x01,0x04,0x0a]` **漏了 02** —— 设备即使确认了头部也会被当作"错位应答"丢掉。现已修正。

## 使用

### 设备信息页的 DFU 诊断按钮

- **⬆ 固件升级 OTA / 🧪 干跑**：完整刷机入口，见上一节「OTA 固件升级（已内置）」。
- **🔓 照抄小程序：0x84→立刻0x8F→重连→解锁**（**不擦除**，**2026-09-25 已按抓包校准**）：先可选做识别（`0x8F→SN`、`0x8F→SN`、`0x8A→04 0d`、`0x85→01`），然后 `0x84 ENTER_DFU`（→`02`）→ **不等断链、立刻在同一条连接上补发 `0x8F`**（对齐抓包的 59ms 时序）→ 等设备停 BLE / 链路超时断开（`gattserverdisconnected`）→ 自动重连并**重新订阅 FEE2** → `0x85`（应 `02`）→ `0x8C` → `0x81+头96B`（102B 整帧，应 `02`）→ **到此停止**（不发 `0x87`，故不会擦除），只报告"解锁是否被确认"。需先选择固件文件（取头部 96B）。
  - 判据：**`0x85` 必须回 `02`**（回 `01` 说明还在应用态，切换没成功）；解锁帧必须回 `02`。
  - mock 回归：`/tmp/mimic_test.js` 断言"`0x8F` 必须在断链前同连接发出"与"`02` 应答不被 expect 丢弃"。
  - 历史（已废弃的写法）：我们曾在 `0x84` 后**等重连完成再发 `0x8F`**，设备只回 `0a+SN`，切换从未发生 ⇒ 解锁永远静默。
- **🔬 DFU 应答通路测试**：对比 FEE2 通知与 `FEE1.readValue()` 读回。**已测结论**：`read=true` 但每次读都 `GATT operation not permitted` ⇒ 读回通路不可用，应答只走通知，该线索排除。
- **📏 帧长边界测试**：只读命令 `0x8A`+填充，粗扫 7→145B + 细扫。**已测结论**：应用态从约 19B 起静默（旧固件收包缓冲小），DFU 态 145B 仍有应答 ⇒ **帧长不是解锁失败的原因**（抓包也证明小程序就是单帧发 102B/134B）。
- **RX 丢帧留痕**：`onDfuReceive` 会把 **CRC 校验失败**、**长度字段非法**而被丢弃的帧写进日志（此前静默丢弃，会让人误判成"设备没回"）。
- 设备信息页的「固件版本 / SN」由 DFU 服务（`FEE0`，命令 `0x8A` / `0x8F`）读取。

## 自检

- **语法**：把 `<script>` 内容交给 `new Function(...)` 解析（无异常即通过）；
